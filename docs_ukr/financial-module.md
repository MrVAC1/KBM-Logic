# Фінансовий модуль (KBM Logic)

Цей документ описує роботу фінансового рушія після міграції на MongoDB Atlas та додавання доходів/витрат (**Transactions**) у базові формули Earned Value Management (EVM).

---

## 1) Моделі даних (MongoDB Atlas)

### Схема Project (поля для фінансів)
- `fixedCosts[]` – планові витрати з `amount`, `currency` та `frequency` (`one-time`, `daily`, `weekly`, `monthly`, `yearly`); зберігаються всередині проєкту як базові витрати.
- `members[].userId.monthlySalary` – місячна зарплата; конвертується у **денну ставку** за допомогою `workSchedule` (робочі дні/тиждень, години/день). Денна ставка входить до AC.
- `workSchedule` – визначає перерахунок зарплат у ставки та розподіл PV у часі.
- `evmSnapshots[]` – кешовані точки PV/AC/EV для історичних дат (прискорює побудову S-кривої).
- `cumulativeActualCost` – кешована сума AC.
- `deadline` – цільова дата завершення; використовується для визначення кінця проєкції PV.
- Похідний об’єкт `financials` (відповідь `/projects/:id/stats`) – не зберігається як поле, але повертається клієнтам з PV/AC/EV, відхиленнями та залишком бюджету.

### Схема Transaction
- Поля: `projectId`, `amount`, `type` (`'+'` = Доходи, `'-'` = Витрати), `source`, `date` (immutable), `authorId`, `description`.
- Вплив:
  - `type: '+'` (Доходи) збільшує доступний/залишковий бюджет.
  - `type: '-'` (Витрати) входить до **AC**.
- Індекси для Atlas: `{ projectId, type, date }` та `{ projectId, date }`.

### Схема Expense
- Поля: `projectId`, `name`, `amount`, `frequency` (`daily`, `weekly`, `monthly`, `yearly`), `createdBy`, `updatedBy`, часові мітки.
- Регулярні витрати: застосовуються за частотою до AC.
- Разові витрати: фіксуються як окремий запис Expense (без повторів після дати створення) або як елемент `fixedCosts` з `frequency: 'one-time'`.

---

## 2) Ядро EVM та формули

- **PV (Planned Value)** – Базовий бюджет розподіляється по тривалості проєкту від старту до дедлайну (або ефективного дедлайну) на основі бюджетів задач (estimate hours × середня погодинна ставка із зарплат). PV продовжується у майбутнє для проєкції.
- **EV (Earned Value)** – `Загальний бюджет * % завершених задач` (реалізовано як сума бюджетів задач зі статусом Done на цільову дату).
- **AC (Actual Cost)** – `Sum(Daily Salaries from Start to Now) + Sum(Fixed Costs) + Sum(Negative Transactions)`
  - Зарплати: денні ставки з `members[].userId.monthlySalary` та `workSchedule`.
  - Фіксовані/регулярні витрати: `fixedCosts` і `expenses`, застосовані за частотою.
  - Негативні транзакції: усі `type: '-'` до цільової дати.
  - **"Цього місяця"**: AC перераховується для вибраного періоду, сумуючи ці три джерела в межах фільтру.
- **Відхилення**
  - SV (Schedule Variance) = `EV - PV`
  - CV (Cost Variance) = `EV - AC`

---

## 3) Метрики фінансового стану

- **Burn Rate** – Середні щоденні витрати за останні 30 днів: ковзаюче AC (зарплати + регулярні витрати + `type: '-'` транзакції) в межах вікна.
- **Runway** – `Залишковий бюджет / Денний Burn Rate` (нескінченність, якщо витрати нульові).
- **Remaining Budget** – `(Початковий/базовий бюджет + Усі доходи з транзакцій) - Actual Cost`

---

## 4) S-крива (адаптивна логіка)

- **Адаптивна дискретизація**
  - Проєкти < 2 місяців: щоденні точки.
  - Багатоступенева логіка для довших проєктів: тижнева (<6 міс), двотижнева (<2 роки), місячна (<5 років), квартальна (5+ років). Проєкти > 2 років, відповідно, агрегуються щонайменше щомісяця.
- **Прогноз у майбутнє**
  - PV йде до дедлайну/ефективної кінцевої дати.
  - AC (та EV) зупиняються на сьогодні; для майбутніх точок відображається лише PV.

---

## Примітки та зберігання

- Усі колекції (`projects`, `transactions`, `expenses`, `tasks`, `users`) зберігаються в **MongoDB Atlas**.
- Індекси транзакцій/витрат оптимізовані під AC і бюджет; історичні PV/AC/EV кешуються в `evmSnapshots` для швидких вибірок.
