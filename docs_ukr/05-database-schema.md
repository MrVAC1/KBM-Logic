# Схема Бази Даних

## Огляд

KBM Logic v3.0 використовує **MongoDB Atlas** з **Mongoose ODM** для моделювання даних. Цей документ надає довідник для ключових схем бази даних та їх зв'язків.

## Основні Моделі

### Project

Модель **Project** є центральною сутністю, що містить всю конфігурацію проекту, членів, ролей та фінансові дані.

#### Ключові Поля

**`workSchedule`** - Критично для фінансових розрахунків (ОБОВ'ЯЗКОВЕ):
- `workingDays`: Масив номерів днів (0=Неділя, 6=Субота), за замовчуванням `[1,2,3,4,5]` (Пн-Пт)
- `hoursPerDay`: Години роботи на день (за замовчуванням: 8)
- Використовується EVM движком для розрахунку робочих днів та годинних ставок
- **Валідація:** Поле має бути встановлене при створенні проєкту

**`roles`** - Дані компенсації ролей:
- `currentRate`: Поточна місячна зарплата
- `salaryHistory`: Історичні зміни ставок з ефективними датами
- Використовується для розрахунку AC з історичною точністю

**`evmSnapshots`** - Кешовані розрахунки EVM:
- Генеруються щодня через cron job
- Регенеруються коли створюються ретроактивні транзакції
- Використовуються для даних графіків S-Кривої

### Transaction

Модель **Transaction** зберігає фінансові транзакції (доходи та витрати).

#### Ключові Поля

**`effectiveDate`** - Дата фінансового впливу (ОБОВ'ЯЗКОВЕ):
- Використовується для розрахунку AC (коли транзакція впливає на бюджет)
- Може бути встановлена на минулі дати для ретроактивних записів
- Запускає регенерацію снапшотів якщо в минулому
- **Валідація:** Поле є обов'язковим при створенні транзакції

**`date`** - Дата транзакції (ОБОВ'ЯЗКОВЕ):
- Встановлюється в значення `effectiveDate` для зворотної сумісності
- Незмінне (не можна змінити)
- **Валідація:** Поле є обов'язковим при створенні транзакції

**`source`** - Джерело транзакції (ОБОВ'ЯЗКОВЕ):
- Опис джерела транзакції (наприклад, "Client Payment", "AWS Invoice")
- **Валідація:** Поле є обов'язковим при створенні транзакції

**`createdAt`** - Аудит-трек:
- Коли транзакція була введена в систему
- Зберігається для цілей аудиту
- Не використовується у фінансових розрахунках

### Task

Модель **Task** представляє робочі елементи на Kanban дошці.

#### Ключові Поля

**`plannedValue`** та **`plannedCost`**:
- Обидва зберігають однакове значення (бюджет задачі)
- Розраховується: `Тривалість (години) × Середня Годинна Ставка`
- Використовується для розрахунків PV та EV

**`timeLogs`**:
- Масив записів відстеження часу
- Кожен запис відстежує одну сесію таймера
- `duration` розраховується коли таймер зупиняється

**`risk`**:
- Автоматично розрахована оцінка ризику
- `auto_score = probability × impact`
- Коригується движком ризиків на основі дедлайну/бюджету

### User

Модель **User** зберігає інформацію про обліковий запис користувача.

#### Ключові Поля

**`uid`** - Firebase User ID:
- Основний ідентифікатор з Firebase Auth
- Використовується для аутентифікації та авторизації
- Унікальний для всіх користувачів

### Expense

Модель **Expense** зберігає повторювані фіксовані витрати.

#### Ключові Поля

**`frequency`** - Частота нарахування:
- `daily`: Нараховується кожен робочий день
- `weekly`: Нараховується раз на тиждень
- `monthly`: Нараховується раз на місяць (21 робочий день)
- `yearly`: Нараховується раз на рік

Використовується розрахунком AC для визначення коли витрата впливає на бюджет.

## Зв'язки

### Project → Members → Users

```
Project.members[].userId → User._id
```

**Тип Зв'язку:** Один-до-Багатьох (Проект має багато Членів, кожен посилається на одного Користувача)

### Project → Tasks

```
Task.projectId → Project._id
```

**Тип Зв'язку:** Один-до-Багатьох (Проект має багато Задач)

### Project → Transactions

```
Transaction.projectId → Project._id
```

**Тип Зв'язку:** Один-до-Багатьох (Проект має багато Транзакцій)

## Стратегія Індексування

### Оптимізація Продуктивності

Індекси оптимізовані для загальних шаблонів запитів:

1. **Пошук Проектів:** `projectId` індексовано на всіх пов'язаних моделях
2. **Фільтрація за Статусом:** `status` індексовано на моделі Task
3. **Запити за Діапазоном Дат:** `effectiveDate`, `deadline` індексовано
4. **Посилання на Користувачів:** `userId`, `uid`, `email` індексовано

## Найкращі Практики

1. **Використовуйте Індекси:** Завжди запитуйте за індексованими полями коли можливо
2. **Популяція Обмежено:** Використовуйте `.lean()` для read-only запитів
3. **Пакетні Операції:** Використовуйте bulk операції для множинних оновлень
4. **Валідація Ранно:** Валідуйте дані перед операціями з базою даних
