# Документація бізнес-логіки

Цей документ пояснює основні движки бізнес-логіки, що працюють у KBM Logic: Движок динамічних ризиків, система Бюджетування S-кривою та Шлюз доступу.

---

## Движок динамічних ризиків

**Розташування**: `server/services/riskEngine.js`

Движок ризиків автоматично перераховує оцінки ризиків завдань на основі факторів реального часу, таких як наближення дедлайну та статус бюджету. Це забезпечує актуальність оцінок ризиків під час зміни умов проекту.

### Формула оцінки ризику

**Розрахунок базової оцінки**:
```
Base Score = probability × impact
```

Де:
- **probability**: Ручне введення (шкала 1-5)
- **impact**: Ручне введення (шкала 1-5)
- **Діапазон результату**: 1-25

### Логіка автоматичної корекції

Система автоматично коригує оцінки ризиків, коли виконуються певні умови:

#### 1. Модифікатор часу (наближення дедлайну)

**Умова спрацювання**:
- У завдання встановлений дедлайн
- Днів до дедлайну < 2
- Статус завдання не "Done"

**Дія**:
```javascript
newProbability = Math.min(5, currentProbability + 1)
autoAdjustReason = "Deadline approaching (< 2 days)"
```

**Приклад**:
- Початкова ймовірність: 3
- Після корекції: 4 (обмежено 5)
- Початкова оцінка: 3 × 4 = 12
- Нова оцінка: 4 × 4 = 16 (збільшення на 33%)

#### 2. Модифікатор бюджету (майбутнє покращення)

Модифікатор бюджету запланований, але ще не повністю реалізований. Коли буде увімкнено, він буде:

**Умова спрацювання**:
- Фактична вартість проекту > 100% запланованого бюджету
- Завдання не "Done"

**Дія**:
- Збільшити ймовірність на 1 (обмежено 5)
- Встановити `autoAdjustReason`, щоб вказати перевитрату бюджету

### Процес розрахунку ризику

1. **Оновлення завдання викликає перерахунок**
   - Кожного разу, коли завдання створюється або оновлюється
   - Движок ризиків запускається автоматично

2. **Перевірка тиску часу**
   - Обчислює дні до дедлайну
   - Застосовує модифікатор часу, якщо потрібно

3. **Перевірка статусу бюджету** (якщо увімкнено)
   - Порівнює фактичну та заплановану вартість
   - Застосовує модифікатор бюджету, якщо виявлено перевитрату

4. **Обчислення фінальної оцінки**
   - Використовує скориговану ймовірність та вплив
   - Зберігає `auto_score` в task.risk

5. **Позначка автоматичної корекції**
   - Встановлює `isAutoAdjusted: true`, якщо застосовано модифікатори
   - Зберігає причину в `autoAdjustReason`

### Матриця оцінок ризику

| Діапазон оцінки | Рівень ризику | Індикатор кольору |
|-----------------|---------------|-------------------|
| 1-5             | Низький       | Зелений           |
| 6-10            | Середній      | Жовтий            |
| 11-15           | Високий       | Помаранчевий      |
| 16-20           | Дуже високий  | Червоний          |
| 21-25           | Критичний     | Темно-червоний    |

### Приклад розрахунку

**Початковий стан**:
- Ручна ймовірність: 3
- Ручний вплив: 4
- Базова оцінка: 3 × 4 = 12 (Високий ризик)

**Після наближення дедлайну** (< 2 дні):
- Скоригована ймовірність: 4 (+1 від модифікатора часу)
- Вплив: 4 (не змінено)
- Автоматична оцінка: 4 × 4 = 16 (Дуже високий ризик)
- `isAutoAdjusted`: true
- `autoAdjustReason`: "Deadline approaching (< 2 days)"

## EVM Бюджетування (S-крива)

**Розташування**: `server/services/budgetEngine.js`

Система використовує принципи Earned Value Management (EVM) з розрахунками S-кривої для відстеження запланованих та фактичних витрат з часом.

### Запланована вартість (PV) - Розрахунок S-кривої

S-крива представляє кумулятивні заплановані витрати протягом життєвого циклу проекту.

#### Формула

Для кожного дня в часовій шкалі проекту:
```javascript
Daily Planned Value = Daily Fixed Costs + Daily Task Costs

Cumulative PV = Sum of all daily values from start date
```

#### Компоненти

**1. Розподіл фіксованих витрат**:
- Щомісячні витрати: `daily = amount / 30`
- Щотижневі витрати: `daily = amount / 7`
- Щоденні витрати: `daily = amount`
- Річні витрати: `daily = amount / 365`

**2. Розподіл витрат на завдання**:
- Кожне завдання має дедлайн та дату створення
- Орієнтовна вартість завдання = `estimatedHours × hourlyRate`
- Щоденна вартість завдання = `estimatedCost / taskDurationDays`
- Включаються лише активні завдання (не "Done")

**3. Кумулятивний розрахунок**:
- Починаючи з `createdAt` проекту
- Сумарний підсумок накопичується кожного дня
- Результат у вигляді S-подібної кривої (повільний старт, зростання, повільне завершення)

### Розрахунок фактичної вартості (AC)

Фактична вартість — це сума двох компонентів:

#### 1. Витрати на логування часу

```javascript
For each task:
  For each time log entry:
    hours = duration (seconds) / 3600
    cost = hours × hourlyRate
    totalCost += cost
```

#### 2. Ручні транзакції

```javascript
For each transaction:
  if (type === '+') totalCost += amount
  if (type === '-') totalCost -= amount
```

**Фінальна AC**:
```
Actual Cost = Time Log Costs + Transaction Sum
```

### Структура кривої запланованої вартості

Функція `calculatePlannedValue()` повертає масив щоденних точок даних:

```javascript
[
  { date: "2024-01-01", plannedValue: 100 },
  { date: "2024-01-02", plannedValue: 210 },
  { date: "2024-01-03", plannedValue: 325 },
  // ... продовжується для тривалості проекту
]
```

Кожна точка представляє кумулятивні заплановані витрати до цієї дати.

### Приклад S-кривої

**Часовий проміжок проекту**: 6 місяців (180 днів)

- **Дні 1-30**: Повільне зростання (0% → 15% бюджету)
- **Дні 31-120**: Стабільний прогрес (15% → 70% бюджету)
- **Дні 121-180**: Фаза завершення (70% → 100% бюджету)

Це створює характерну S-подібну форму при побудові графіка.

### Розрахунок відхилення бюджету

```
Variance = Actual Cost - Planned Value
```

- **Позитивне відхилення**: Перевитрата (витрачається більше, ніж заплановано)
- **Негативне відхилення**: Економія (витрачається менше, ніж заплановано)

## Шлюз доступу

**Розташування**: `server/controllers/projectController.js` (getProjectDetails)

Шлюз доступу контролює, які дані користувачі можуть бачити на основі їхнього статусу членства та ролі. Він реалізує систему "Безпечного перегляду" для користувачів, що очікують/гостей.

### Стани членів

#### 1. Власник

**Характеристики**:
- Створив проект
- Має всі дозволи автоматично
- Не може бути видалений з проекту
- Обходить усі перевірки дозволів

#### 2. Активний член

**Характеристики**:
- Призначена роль (Admin, PM, Developer тощо)
- Має принаймні один дозвіл
- Може бачити повні дані проекту
- Доступ контролюється дозволами RBAC

#### 3. Гість/Очікування

**Характеристики**:
- Приєднався до проекту (член у масиві `members`)
- Має роль "Guest" або нуль дозволів
- Не може бачити чутливі дані
- Показує інтерфейс "Безпечного перегляду"

### Логіка безпечного перегляду

Коли користувач ідентифікований як Гість/Очікування:

**Відповідь Backend** (`getProjectDetails`):
```javascript
{
  id: project._id,
  name: project.name,
  description: project.description,
  status: 'Active',
  role: 'Guest',
  isSafeView: true,  // Прапорець для frontend
  owner: {
    name: owner.displayName,
    avatar: owner.photoURL
  },
  currentUserAccess: {
    role: 'Guest',
    permissions: [],
    isPending: true
  }
  // Явно виключено:
  // - inviteCode
  // - fixedCosts
  // - members (повний список)
  // - tasks
  // - transactions
  // - budget data
}
```

**Поведінка Frontend** (`WorkspaceLayout`):
```javascript
if (currentProject?.isSafeView) {
  return <ProjectOverview project={currentProject} />;
  // Бічна панель прихована
  // Головний вміст приховано
  // Показує лише: Назву проекту, опис, власника, повідомлення "Очікування доступу"
}
```

### Логіка ідентифікації

```javascript
const isOwner = project.ownerId.toString() === userId.toString();

const currentMember = project.members.find(
  m => m.userId.toString() === userId.toString()
);

const userRoleName = currentMember?.roleName || 'Guest';
const userPermissions = currentMember?.permissions || [];

const isGuestOrPending = !isOwner && 
  (userRoleName === 'Guest' || userPermissions.length === 0);
```

### Потік контролю доступу

1. **Користувач запитує дані проекту**
   - Викликає `GET /api/projects/:projectId`

2. **Backend перевіряє членство**
   - Знаходить користувача в масиві `project.members`
   - Перевіряє, чи є користувач власником

3. **Визначає рівень доступу**
   - Власник → Повний доступ
   - Активний член → Доступ на основі дозволів
   - Гість/Очікування → Лише безпечний перегляд

4. **Повертає відповідні дані**
   - Повні дані для власників/активних членів
   - Обмежені дані для гостей/очікуючих

5. **Frontend відображає**
   - Повний workspace для активних членів
   - Безпечний перегляд для гостей/очікуючих

### Доступ на основі дозволів

Навіть для активних членів доступ контролюється детальними дозволами:

- `can_view_dashboard` - Бачити сторінку dashboard
- `can_view_tasks` - Бачити Kanban-дошку
- `can_view_risks` - Бачити оцінки ризиків
- `can_view_financial` - Бачити дані бюджету/фінансів
- `can_track_time` - Логувати час на завданнях
- `can_create_tasks` - Створювати нові завдання
- `can_edit_tasks` - Модифікувати завдання
- `can_delete_tasks` - Видаляти завдання
- `can_edit_budget` - Модифікувати бюджет/транзакції
- `can_manage_roles` - Змінювати ролі членів
- `can_invite_users` - Запрошувати нових членів
- `can_manage_settings` - Редагувати налаштування проекту
- `can_delete_project` - Видаляти проект

Кожна кінцева точка API перевіряє необхідні дозволи перед поверненням даних.

## Точки інтеграції

### Інтеграція движка ризиків

- **Викликається**: Операції створення/оновлення завдань
- **Викликається з**: `taskController.js` (createTask, updateTask)
- **Оновлює**: Документ завдання з перерахованими оцінками ризиків

### Інтеграція движка бюджету

- **Викликається**: Запит статистики dashboard
- **Викликається з**: `financialController.js` (getDashboardStats)
- **Використовується для**: Візуалізації S-кривої, розрахунків відхилень бюджету

### Інтеграція шлюзу доступу

- **Викликається**: Запит деталей проекту
- **Викликається з**: `projectController.js` (getProjectDetails)
- **Застосовується**: RBAC middleware на всіх захищених маршрутах

---

## Підсумок

Ці три движки працюють разом, щоб забезпечити:

1. **Проактивне управління ризиками** - Автоматичні корекції оцінок ризиків
2. **Фінансова видимість** - Відстеження запланованої та фактичної вартості
3. **Безпечний контроль доступу** - Безпечний перегляд для очікуючих членів, детальні дозволи для активних членів

Всі движки працюють автоматично на основі змін даних — ручне втручання не потрібно.
